# 第三章：数据库设计分析

## 从需求到数据

在上一章中，我们完成了项目的需求分析，明确了博客系统需要包含哪些功能、需要管理哪些数据。现在，我们要在这个基础上，进一步细化数据模型，设计出能够支撑这些功能的数据库结构。

数据库设计是整个开发过程中至关重要的一环。如果说需求分析回答的是"我们要做什么"的问题，那么数据库设计回答的就是"我们要怎么做"的问题。设计得当的数据库结构，可以让后续的开发工作事半功倍；设计失误的数据库结构，则可能让你在开发过程中不断遇到各种棘手的问题，甚至需要推倒重来。

## Django 的 ORM 机制

在正式设计数据库之前，让我们先了解一下 Django 是如何处理数据库的。

传统的 Web 开发中，如果要操作数据库，我们需要编写 SQL 语句。比如，要查询所有文章，SQL 可能是这样的：

```sql
SELECT title, content, created_time FROM blog_post WHERE status = 'published';
```

要插入一篇新文章，可能需要这样：

```sql
INSERT INTO blog_post (title, content, created_time, category_id) 
VALUES ('Django入门', '这是一篇关于Django的文章...', '2024-01-01', 1);
```

这种方式的缺点是：SQL 语句散落在代码的各个角落，难以维护；不同数据库的 SQL 语法可能有细微差别，给迁移带来麻烦；开发者需要同时熟悉业务逻辑和数据库知识。

Django 提供了 ORM（Object Relational Mapping，对象关系映射）来解决这个问题。简单来说，ORM 就是把数据库表映射为 Python 类，把表中的每一行映射为类的实例，把表中的每一个字段映射为实例的属性。这样，你就可以用 Python 代码来操作数据库，而不需要编写 SQL 语句。

在 Django 中，我们把定义数据库结构的代码称为"模型"（Model）。每个模型类对应数据库中的一张表，类的属性对应表中的字段。Django 会自动根据模型类的定义，生成相应的 SQL 语句来创建数据库表。

这样做的好处是：

1. **代码更简洁**：不需要写 SQL，直接用 Python 操作数据库
2. **易于维护**：业务逻辑和数据库操作分离，代码结构更清晰
3. **数据库无关**：更换数据库时，只需要修改配置，不需要改动代码
4. **安全性**：Django 的 ORM 会自动处理 SQL 注入等安全问题

## 设计数据模型

现在，让我们回到博客系统的数据库设计。

### 文章模型（Post）

文章是博客系统的核心。先来整理一下文章需要存储哪些信息：

**title（标题）**：文章的名字，应该是一个字符串类型。由于文章标题通常不会太长，选择最大长度 200 个字符应该足够了。

**slug（别名）**：URL 中使用的标识符。比如某篇文章的 URL 是 `example.com/article/django-getting-started`，其中 `django-getting-started` 就是 slug。slug 通常是标题的英文或拼音形式，使用短横线连接。这个字段也应该是字符串类型。

**content（正文）**：文章的具体内容。这个字段可能非常长，普通字符串类型肯定不够用。Django 提供了 `TextField`，专门用于存储大段文本。

**excerpt（摘要）**：文章的简短描述。如果不填写，可以自动从正文中截取前若干字符作为摘要。这个字段不需要太长，500 个字符应该够了。

**created_time（创建时间）**：文章首次发布的时间。这个字段应该是一个日期时间类型。Django 会自动记录这个时间，通常不需要手动设置。

**modified_time（修改时间）**：文章最后被修改的时间。每次修改文章时，这个时间都应该自动更新。

**views（浏览量）**：文章被访问的次数。这是一个整数类型，默认值为 0。

**category（分类）**：文章所属的分类。这是一个外键，指向分类模型。一篇文章必须属于一个分类（外键不能为空）。

**tags（标签）**：文章所属的标签。这是一个多对多关系，一篇文章可以有多个标签，一个标签也可以关联多篇文章。

**author（作者）**：文章的作者。对于我们的简单博客系统，作者就是管理员自己。Django 自带了用户模型，我们可以直接使用。这里也是一个外键，指向用户模型。

### 分类模型（Category）

分类用来对文章进行一级组织。分类需要的信息比较简单：

**name（名称）**：分类的显示名称，比如"技术分享"。字符串类型，限制最大长度。

**slug（别名）**：URL 中使用的标识符。

**created_time（创建时间）**：分类创建的时间。

分类和文章是一对多关系：一个分类可以有多篇文章，但每篇文章必须属于一个分类。

### 标签模型（Tag）

标签用于对文章进行更细粒度的分类。标签需要的信息与分类类似：

**name（名称）**：标签的显示名称。

**slug（别名）**：URL 中使用的标识符。

**created_time（创建时间）**：标签创建的时间。

标签和文章是多对多关系：一篇文章可以有多个标签，一个标签也可以关联多篇文章。

## Django 模型字段详解

了解了需要存储的数据之后，让我们来详细了解一下 Django 提供的各种字段类型。这对于后续编写模型代码至关重要。

### 字符串字段

**CharField**：固定长度的字符串字段。使用时必须指定 `max_length` 参数来限制最大长度。适用于长度有限的字符串，如标题、姓名等。

**TextField**：无限长度的文本字段。不需要指定 `max_length`，适用于文章正文等可能很长的内容。

**SlugField**：slug 专用字段，本质上也是字符串字段。Django 会自动验证 slug 只包含字母、数字、下划线和中划线。

### 数值字段

**IntegerField**：整数类型，用于存储整数值。

**PositiveIntegerField**：正整数类型，只能存储大于等于 0 的整数。适用于浏览量、点击数等不可能为负的场景。

**DecimalField**：精确的小数类型，适用于金额等需要精确计算的场合。

**FloatField**：浮点数类型，存储带小数的数值。

### 日期和时间字段

**DateField**：日期类型，只包含年、月、日。

**TimeField**：时间类型，只包含时、分、秒。

**DateTimeField**：日期时间类型，包含完整的日期和时间。我们在创建时间和修改时间字段时会用到它。

**DurationField**：时间间隔类型，存储一段时间长度。

### 关系字段

**ForeignKey**：外键字段，表示一对多关系。比如一篇文章属于一个分类，分类和文章就是一对多关系。使用时需要指定 `to` 参数指向目标模型，`on_delete` 参数指定删除行为。

**ManyToManyField**：多对多字段，表示多对多关系。比如文章和标签之间就是多对多关系。使用时需要指定 `to` 参数指向目标模型。

**OneToOneField**：一对一字段，类似于 ForeignKey，但两者的关系是一对一而非一对多。

### 其他常用字段

**BooleanField**：布尔类型，存储 True/False 值。

**EmailField**：邮箱类型，会验证输入是否为有效的邮箱格式。

**URLField**：URL 类型，会验证输入是否为有效的 URL。

**ImageField**：图片字段，用于存储图片路径。

**FileField**：文件字段，用于存储文件路径。

**JSONField**：JSON 类型，用于存储 JSON 格式的数据。

## 字段参数详解

除了指定字段类型，Django 还提供了丰富的字段参数来定制字段的行为。了解这些参数，可以让你的模型更加完善。

### 通用参数

**verbose_name**：字段的友好名称，会显示在 Admin 后台等地方。比如 `verbose_name='文章标题'`。

**help_text**：字段的帮助文本，会在表单中显示，帮助用户理解应该如何填写。

**default**：字段的默认值。

**null**：是否允许数据库中存储 NULL 值。对于字符串字段，通常设为 False，因为空字符串比 NULL 更直观。

**blank**：是否允许表单中留空。对于必填字段，通常设为 False。

**choices**：字段的可选值列表。比如性别字段可以定义为 `choices=[('M', '男'), ('F', '女')]`。

**validators**：字段的验证器列表。

**editable**：字段是否可在 Admin 等界面编辑。

**error_messages**：自定义错误消息字典。

### 外键的特殊参数

**on_delete**：指定当被关联对象被删除时的行为。可选值包括：
- `CASCADE`：级联删除，当父对象删除时，子对象也自动删除
- `PROTECT`：保护，如果存在关联对象，则不允许删除
- `SET_NULL`：设为空，需要配合 `null=True` 使用
- `SET_DEFAULT`：设为默认值，需要配合 `default` 使用
- `DO_NOTHING`：什么都不做，这可能导致数据库完整性问题

**related_name**：反向引用的名称。比如在文章模型中定义 `category = ForeignKey(Category, on_delete=CASCADE, related_name='posts')`，就可以通过 `category.posts.all()` 获取该分类下的所有文章。

**related_query_name**：用于反向查询的名称。

### 时间字段的特殊参数

**auto_now_add**：自动设置为创建时的时间，之后不会再改变。

**auto_now**：每次保存时自动更新为当前时间。

## 设计成果：模型定义

现在，让我们把所有分析的结果汇总起来，看看最终的数据模型应该是什么样子。虽然具体的代码要等到创建项目之后才编写，但我们可以先在脑海中形成清晰的结构。

### Post 模型

```
Post
├── title (CharField, max_length=200)        # 文章标题
├── slug (SlugField, unique=True)            # URL 别名，唯一
├── content (TextField)                       # 文章正文
├── excerpt (CharField, max_length=500)      # 文章摘要
├── created_time (DateTimeField, auto_now_add=True)   # 创建时间
├── modified_time (DateTimeField, auto_now=True)      # 修改时间
├── views (PositiveIntegerField, default=0)  # 浏览量
├── category (ForeignKey -> Category)        # 所属分类
├── tags (ManyToManyField -> Tag)             # 所属标签
└── author (ForeignKey -> User)               # 作者
```

### Category 模型

```
Category
├── name (CharField, max_length=100)         # 分类名称
├── slug (SlugField, unique=True)            # URL 别名，唯一
└── created_time (DateTimeField, auto_now_add=True)   # 创建时间
```

### Tag 模型

```
Tag
├── name (CharField, max_length=100)         # 标签名称
├── slug (SlugField, unique=True)             # URL 别名，唯一
└── created_time (DateTimeField, auto_now_add=True)   # 创建时间
```

## 表之间的关系

现在我们来看看这三张表之间的关系。

**Category 和 Post**：一对多关系。一个分类可以有多篇文章，但每篇文章必须属于一个分类。在数据库中，这个关系通过在 Post 表中存储一个指向 Category 表的外键来实现。

**Tag 和 Post**：多对多关系。一篇文章可以有多个标签，一个标签也可以关联多篇文章。在数据库中，这个关系通过一张额外的关联表来实现。Django 的 ORM 会自动创建和管理这张关联表，你不需要手动处理。

**User 和 Post**：一对多关系。一个用户（作者）可以写多篇文章，每篇文章属于一个作者。由于我们使用 Django 自带的用户模型，所以不需要创建额外的用户表。

## 索引和查询优化

在正式设计数据库时，还有一些优化方面的考虑。

### 为常用查询字段添加索引

索引可以大幅提升查询速度，但也会占用额外的存储空间和增加写入的开销。对于我们的博客系统，以下字段可能需要考虑添加索引：

- `slug`：因为每个 slug 都是唯一的，而且经常用于 URL 查询
- `created_time`：因为我们经常需要按时间排序

在 Django 中，只需要在字段定义中添加 `db_index=True` 参数即可创建索引。

### 数据库规范化

数据库规范化是数据库设计中的一个重要概念，目的是消除数据冗余、避免更新异常。我们的模型设计遵循了基本的规范化原则：

- 每个字段都存储原子性的值，没有重复的字段组
- 每个表都有主键（对于 Django 模型，Django 会自动添加 id 主键）
- 关系通过外键而不是在表中复制数据来实现

## 从模型到数据库

Django 的 ORM 有一个很棒的特性：它会根据你定义的模型类，自动生成数据库表结构。这意味着你不需要手动编写 SQL 来创建表，只需要：

1. 定义模型类
2. 运行迁移命令

Django 会分析你的模型定义，生成对应的迁移文件，然后应用这些迁移到数据库，创建相应的表结构。

当模型定义需要修改时（比如增加一个新字段），你只需要修改模型类，然后重新运行迁移命令即可。Django 会生成新的迁移文件，记录这次修改的内容，然后应用到数据库。

这种"代码优先"的数据库管理方式，让数据库版本控制变得轻而易举。你可以像管理代码一样管理数据库的变更，随时回滚到任何一个版本。
